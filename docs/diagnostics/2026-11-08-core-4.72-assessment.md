## 原探针的证据边界

原页复跑输出保存在 JSON 的 `originalDiagnostic`。关键结果与同事一致：自定义圆角/阴影 miss、无 console.warn、compile 25 类立即 0/25、稍后 25/25。其文字写“200ms”，实际定时器为 250ms；因此不是精确的编译耗时测量。

本次 debug 未解析数为 1，对应 Core 自己添加的 `jquan-ready` 标记；它不是缺失的圆角/阴影。绝对数量会受初始扫描、observer 调度与缓存影响，后续用“指定类是否出现”和前后差值判断，而不是断言总数恒为 0。引擎自身标记被当作 unresolved 可列为诊断降噪项。

原页的 enhance 对照生成了 n2 数组，却未把这些类应用到 DOM，因此 0/25 是预期结果，不能证明 enhance 不会处理共享队列。新探针的对照：先 compile 25 类，再 enhance 无新类根，仍为 0；根含一个新类后 enhance，即刻处理全部 25 类，padding 也同步为 987px。

## 建议纳入支线的工作顺序

1. **配置契约与业务令牌，优先处理。** 增加普通圆角、阴影、字号令牌时同时定下值类型、字号复合值、默认项、冲突/覆盖规则；未知键/非法值形成结构化路径诊断，隔离错误值，避免初始化被单个字段中断。首批覆盖 runtime、静态提取、类型、文档与 skill；不能只在运行时塞进 customUtilities 就宣布整个工具链已对齐。
2. **明确动态样式的完成契约。** 将文档中的 compile“立即完成”与实现对齐，评估显式 sync 选项、默认同步的兼容/性能影响，以及独立 flush 或 await 完成接口。观察器增量保留调度能力。同步接口需要测长任务成本；预算 flush 要真实遵守预算，不能把 `maxMs:8` 包在不设上限的 drainAll 外面。
3. **诊断与自动化验收。** 评估只读 `checkClasses` / 显式 trace，分类区分解析 miss、CSS 插入失败和预算跳过；未知业务 class 不逐个 console.warn，避免组件/第三方 class 噪声。开发模式用显式配置，不用 `!isReady()` 推断。截图等待初始 ready 后，还要等待本次动态渲染和队列完成；不要用 webdriver 自动改变编译语义。
4. **版本与目录整理。** 保留纯版本读取的兼容路径，补分发入口说明；对同步副本建立差异清单与可恢复归档，保持现有发布排除规则。

当前晚到配置已有恢复逻辑，不另立“补自愈”功能；先把本次案例固化为回归。20→40 阈值、无头强制同步都属于待验证设计选择，不能作为已经证明有效的修复。

## 修复前，现有项目可用的接法

已插入节点、需要同步补齐当前局部样式时，使用现有 `enhance(root)`；同时会执行该根的插件行为/扫描 hooks，因此调用根应尽量精确。

```js
const root = document.getElementById('function-cards');
// 业务先完成本次 DOM 更新，再同步处理该根现有类。
JquanUI.enhance(root);
console.log(JquanUI.getMetrics().queueSize);
```

需要在 DOM 插入前预热明确类名时，可用已有 `prefetch(classes, { maxClasses, maxBytes, timeoutMs })`；检查 truncated/skipped。accepted 包括“已处理”甚至“未解析”的尝试项，不是逐类成功的保证，仍需用 resolve 或 debug 核对。该方案不等于新增 flush API。圆角/阴影可暂用现有 shortcuts 指向合法任意值；普通 fontSize 扩展仍未实现。
